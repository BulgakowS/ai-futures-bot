# Проєктний API-контракт

Це переважно **цільовий контракт**; реалізовані S02 endpoint-и перелічені нижче. Фінальні URL, поля та версіонування затвердити під час Foundation і генерувати OpenAPI зі справжніх схем. Усі команди авторизуються, валідуються та отримують `request_id`; мутації, що впливають на ордери або баланс, приймають `Idempotency-Key`.

## HTTP ресурси

| Метод і шлях (проєкт) | Призначення | Особливість |
|---|---|---|
| `GET /api/v1/health` | стан API/DB/Redis/market workers | без секретів |
| `GET /api/v1/markets` | інструменти й правила | version, quality, source time |
| `GET /api/v1/markets/{id}/candles` | свічки | UTC range, timeframe, final flag |
| `GET /api/v1/portfolios` | список за режимом | paper за замовчуванням |
| `POST /api/v1/portfolios` | створити віртуальний портфель | mode=`paper`, стартовий баланс |
| `POST /api/v1/portfolios/{id}/reset` | нова епоха paper-портфеля | підтвердження, журнал збережено |
| `GET/POST /api/v1/bots` | список/створення | версія стратегії й risk profile |
| `POST /api/v1/bots/{id}/start` | запуск | перевірка даних та конфігурації |
| `POST /api/v1/bots/{id}/pause` | призупинення | нові входи зупинено |
| `GET /api/v1/positions` | відкриті позиції | mode/portfolio filters |
| `GET /api/v1/orders` | ордери/fills | status, correlation ID |
| `GET /api/v1/decisions` | AI/strategy/risk журнал | reason codes |
| `POST /api/v1/risk/kill-switch` | аварійне блокування | server-side state + audit |
| `GET/POST /api/v1/backtests` | запуски й результати | dataset/config/seed |
| `GET /api/v1/analytics` | метрики та equity curve | методика, витрати, період |

У MVP не експонувати endpoint для live-ордерів. Якщо згодом він з'явиться, він має окремий namespace й незалежний server-side gate. `POST /bots/start` не повинен бути прихованим способом увімкнення Live.

## Події до frontend

SSE або WebSocket канал (вибір на етапі Foundation) передає `market.updated`, `data.degraded`, `bot.status`, `decision.created`, `risk.rejected`, `order.updated`, `position.updated`, `portfolio.updated`, `alert.created`. Кожна подія має `event_id`, `aggregate_id`, `occurred_at`, `sequence`, `schema_version`. Клієнт після reconnect читає snapshot HTTP і продовжує з останнього cursor; повтор події не подвоює UI-стан.

## Помилки та безпека

Стандартна помилка: `code`, `message`, `details` без секретів, `request_id`, `retryable`. Не зводити `DATA_STALE`, `RISK_REJECTED`, `INSUFFICIENT_MARGIN`, `BROKER_UNKNOWN` та `RATE_LIMITED` до одного generic error. Для команд перевіряти власність портфеля, режим, конфігураційну версію й допустимий стан. Навіть локальний API має захист від випадкового доступу через зовнішній інтерфейс; конкретний механізм auth визначити на етапі Foundation.

## Реалізовано S02

- `GET /api/v1/health/live`: liveness процесу, UTC timestamp.
- `GET /api/v1/health` і `/api/v1/health/ready`: 200 або 503; database, migrations, Redis, AppState, trading heartbeat.
- `GET /api/v1/state`: persisted instance_id/mode/kill_switch/config_version/created_at, без секретів.
- `GET /docs`, `/openapi.json`: актуальні схеми.
- Усі HTTP-запити отримують server-generated UUID у `X-Request-ID`; усі майбутні мутації автоматично вимагають backend Bearer token. Відсутній/невірний token → 401 AUTH_REQUIRED. Браузер не має отримувати bootstrap secret.

Token обмежений локальним однокористувацьким backend; browser session/proxy буде додано S06. Idempotency для фінансових команд, SSE, ownership та торгові endpoint-и ще не реалізовані.

S03 public cache: `GET /api/v1/markets` і `/api/v1/markets/{symbol}/{ticker,candles,funding,depth,quality}`. Підтримується BTC_USDT; candles `timeframe=1m|5m|15m`, `limit=1..2000`. Decimal поля — JSON strings; source_time UTC відрізняється від received_at. Відсутній snapshot →503; stale snapshots повертаються з quality/trade_eligible=false. Запити читають cache і не викликають MEXC. Depth fills лише estimated REST snapshot; funding current не є settlement rate. Детальні контракти — S03 у IMPLEMENTATION.md.

S04 paper backend: `GET/POST /api/v1/portfolios`, `GET /api/v1/portfolios/{id}`, `POST /api/v1/portfolios/{id}/reset|orders`, `POST /api/v1/portfolios/{id}/positions/{position_id}/close`, `POST /api/v1/portfolios/{id}/orders/{order_id}/cancel`, `GET /api/v1/portfolios/{id}/orders|positions|decisions|ledger|risk|fills`, `GET /api/v1/risk`, `POST /api/v1/risk/kill-switch`, `POST /api/v1/markets/{symbol}/rules/acknowledge`. Поточні open/close команди приймають `idempotency_key` у JSON body, не в HTTP `Idempotency-Key`; ключ унікальний на портфель через усі епохи. Успішна команда повертає `{intent,risk,order}`, відхилена — `order=null` із machine-readable `risk.reason`. Базовий Bearer token — локальний backend auth, browser session/ownership ще немає. Усі суми/кількості повертаються рядками Decimal; кожен fill має provenance та risk verdict через order.

Dashboard Paper summary (2026-10-21): кожен `GET /api/v1/portfolios` і `GET /api/v1/portfolios/{id}` додає `initial_deposit` та `realized_pnl_net` як Decimal strings поточної епохи (`wallet_balance − initial_deposit`), а `total_pnl_net` дорівнює `equity − initial_deposit` або `null`, якщо valuation невідома. Проведені fees і funding входять до wallet. `unrealized_pnl` також лишається `null` за `DATA_STALE`/`FUNDING_UNRESOLVED`; після reset результат нової епохи не включає старий. Боти визначаються окремим `GET /api/v1/bots` і зв'язуються з цими summary за `portfolio_id`; окремі портфелі без ботів не приписуються ботам.

S10D/F4: `positions[].liquidation_estimate` є Decimal string або `null`. `positions[].liquidation_provenance` містить `model=model_estimate`, `status=estimated|unknown`, reason, tier level/cap/contracts, mmr/imr/max leverage, raw rules hash/config version, mark event/source, UTC час і припущення. Це сценарна оцінка; API не обіцяє біржовий `liquidatePrice`. Невідомий tier блокує новий ордер через risk verdict `RISK_TIER_UNKNOWN`; protective fill має `provenance.liquidation_model` та окремо проведену liquidation fee.

S10B/F3 додає до portfolio summary `funding_gap_time` (UTC ISO або `null`) і `funding_unresolved_reason` (`COVERAGE_UNPROVEN|JOURNAL_MISMATCH|SETTLEMENT_UNPOSTED|null`). Якщо coverage не доведено для всіх held intervals поточної епохи, `valuation_status=FUNDING_UNRESOLVED`, `pending_funding_status=unresolved`, `equity=null`; новий open отримує `risk.reason=FUNDING_UNRESOLVED`, reset повертає 409 `FUNDING_UNRESOLVED` після закриття позицій. `GET /markets/{symbol}/funding` і далі показує лише current та latest 20 як UI cache, не durable coverage; watermark не додавався до public market API. Ledger provenance funding містить confirmed rate raw hash/config version і `estimated_prior_final_1m_close` candle ID.

S05 paper bots: `GET/POST /api/v1/bots`, `GET /api/v1/bots/{id}`, `POST /api/v1/bots/{id}/config|ready|start|pause|stop`, `GET /api/v1/bots/{id}/decisions`. `POST /bots` вимагає `name`, `deposit`, повний rule-based `config` зі [Стратегій](STRATEGIES.md); `risk_profile` можна опустити для чинного Paper default. Запит атомарно створює окремий paper портфель. Конфігурація додається новою незмінною версією лише поза RUNNING/RISK_HALTED; `active_version` фіксується при start. Рішення повертає `action`, стратегічний `reason`, `risk_reason`, candle ID/hash і, за наявності, intent/risk/order IDs. `WAIT` не надсилає ордер. Боти приймають лише BTC_USDT, live endpoint відсутній. Список і детальний GET повертають останню конфігурацію та тип бота.

S05 доповнення 2026-10-21: `POST /bots` також приймає `config={kind:"learned_paper",max_position_notional_usdt:"...",leverage:"2",stop_loss_pct:"...",take_profit_pct:"..."}` для **неактивної Paper чернетки**. Усі чотири числові значення обов'язкові Decimal рядки; notional додатний, `1 ≤ leverage ≤ 3`, відсотки >0 і <100. Ключі `stop_loss_pct` і `take_profit_pct` збережено для сумісності вже створених `DRAFT`; для `learned_paper` вони означають верхні межі відсоткової відстані SL/TP від entry, а не точні рівні. Майбутня схвалена модель може запропонувати окремі точні `0 < stop_distance_pct ≤ stop_loss_pct` та `0 < target_distance_pct ≤ take_profit_pct`; цей API ще не приймає такої пропозиції і не виконує її. Ліміт notional означає повну вартість однієї позиції **вже з урахуванням плеча**, не маржу. `risk_profile` можна опустити, тоді діє чинний Paper default. `GET /bots` і `GET /bots/{id}` включають останній `config`, `bot_kind=rule_based|learned_paper` та `readiness_code`. Для `learned_paper` `ready/start/config` повертають 409 `MODEL_NOT_APPROVED`; worker не надсилає Paper intent/order навіть при примусовому `RUNNING`. Плече в чернетці не дозволяє обійти майбутній Risk Engine або актуальні правила інструмента. Старий `StrategyConfig` і запуск rule-based ботів збережені.

S06 local web BFF: браузер викликає лише same-origin `/api/backend/<allowlisted path>`; Next.js server додає `BACKEND_AUTH_TOKEN` для запиту до `BACKEND_URL` і не серіалізує token у клієнтський bundle. Дозволені тільки потрібні UI GET та POST для paper портфелів, ботів, позиції close й kill switch; довільного proxy та live маршруту немає. POST вимагає `application/json`, Origin рівний `http://localhost:3030` або `http://127.0.0.1:3030` відповідно до Host, а Host має бути loopback:3030. Compose публікує web лише на `127.0.0.1:3030`. BFF зберігає HTTP status/body backend, використовує `no-store` та 10s timeout. У межах однокористувацького local MVP немає browser account/session чи віддаленого доступу; такий доступ потребує окремого auth/TLS дизайну.

S25 exchange credential UI/BFF: allowlist перевіряє **пару path+method**. Для `/exchange-credentials` доступні лише GET/POST; для `/{id}` лише GET; для `/{id}/rotate` лише PUT; для `/{id}/revoke` лише POST; для `/bots/{id}/live-credential` лише GET/PUT. Усі ці запити проходять той самий loopback Host, exact Origin для мутацій, server-side Bearer token, `cache: no-store` і `Cache-Control: no-store`, включно з ранніми помилками BFF. UI не зберігає key/secret у localStorage, не має reveal endpoint і показує лише masked metadata; вибір credential для Paper бота не змінює його Paper config/start і завжди має `live_allowed=false`. Browser session auth/TLS для віддаленого доступу не реалізовано.

S07 AI backend: `POST /api/v1/ai/analyses` приймає `{analysis_id, portfolio_id, policy}` з `AiPolicy` у OpenAPI; mutation вимагає backend Bearer token. `GET /api/v1/portfolios/{portfolio_id}/ai/analyses` повертає останні 100 sanitized decision summaries без OpenAI key, raw response або prompt text. Результат має `status`, `action`, `reason`, model/prompt version, `context_id`, validated proposal, причинні paper intent/risk/order IDs та `risk_reason`. `AI_ENABLED=false` або відсутній `OPENAI_API_KEY` → `WAIT/AI_DISABLED`. `submit_to_paper=false` за замовчуванням; при `true` тільки `PaperService.submit()` може створити ордер. Ці шляхи не внесені в S06 BFF allowlist і не доступні з UI. Деталі й межі бюджету — [AI Engine](AI_ENGINE.md).

S08 backtest backend: `POST /api/v1/backtests/datasets` з `{symbol,timeframe,start_utc,end_utc}` фіксує наявні REST-final DB свічки, `GET /api/v1/backtests/datasets/{id}` повертає snapshot. `POST /api/v1/backtests/datasets/{id}/runs` з `{config,risk_profile,deposit,seed}` повертає `{id,dataset_id,report_checksum,report}`; `GET /api/v1/backtests/runs/{id}` читає його. `POST /api/v1/backtests/compare` з `{run_ids}` вимагає спільний dataset, інтервал, депозит, risk profile, cost assumptions, seed і config version. Усі POST вимагають backend Bearer token; GET не змінюють стан. S06 BFF allowlist не розширено, browser UI для replay немає. Backtest не створює Paper ордери й не викликає OpenAI/MEXC; деталі — [Backtesting](BACKTESTING.md).

S10C/F1–F2: `GET /api/v1/portfolios/{id}/fills` повертає в `provenance` `model=estimated_fill`, `depth_id`, `depth_version`, `ticker_id`, `rules_version`, `rules_config_version`, `fee_source=public_contract_rules_taker`, `fee_rate`, `fee_rate_mode`, `fee_rate_type`, `public_maker_rate`, `public_taker_rate`, `trading_fee`, scenario slippage й `limit_model` для crossing limit. Fee ledger має той самий provenance та точну протилежну проводку. В order payload є `fill_model=estimated_rest_snapshot`, а для limit — `limit_model=crossing_rest_book_no_queue`; passive limit лишається `PENDING`, market без обсягу — `NO_LIQUIDITY`. Risk verdict snapshot містить застосовані fee source/rate/mode. Зміна public rules вимагає `POST /api/v1/markets/{symbol}/rules/acknowledge` із точним `expected_version`; unsupported fee mode/tier або inactive state дають `RULES_INVALID`. Неповна чи конфліктна книга дає `DEPTH_INVALID` або `DEPTH_STALE` до брокера. Це public scenario estimate, не account-specific fee або підтверджений біржовий fill.

S11/N4b research GET: `GET /api/v1/research/forecasts` (останні 20, `limit=1..50`), `/latest` і `/{forecast_id}` читають лише BTC_USDT `news_forecast`/`news_forecast_proposal`. На **кожному GET** потрібний backend Bearer token; чужий/відсутній token →401, відсутній ID →404. Відповідь має `mode=collect-only`, `trading_enabled=false`, UTC anchor/created, фіксований 4h horizon, causal IDs, status/direction/reason/quality, class probabilities, model/artifact/dataset/config/source provenance, market/news IDs і optional proposal. `test_fixture=true` позначає лише N4a synthetic approval; це не підтверджена якість MEXC чи дозвіл на виконання. Порожній журнал дає `items=[]`/`forecast=null`; endpoint не запускає inference, polling або Paper. Same-origin BFF дозволяє тільки ці три GET path, без POST і без довільного query proxy; перед доступом до runtime потрібне застосування міграції у погодженому середовищі.

## S21 draft Live pilot settings API (2026-10-20)

`GET /api/v1/bots/{id}/live-pilot-settings` повертає `{bot_id,draft,version,created_at,config_version,live_allowed:false,reason}`. Без запису `draft/version/created_at/config_version = null`, `reason=PILOT_CONFIG_MISSING`; після збереження `reason=LIVE_DISABLED`. `PUT` на тому ж шляху потребує backend token і повного JSON тіла `{max_pairs,per_pair_notional,aggregate_notional,max_leverage,take_profit_pct,stop_loss_pct,max_daily_loss,max_round_trip_cost_pct}`. Ліміти мають `{unit:"USDT"|"PCT_EQUITY",value:"decimal-string"}`; інші Decimal поля теж передаються рядками. `PCT_EQUITY` використовує відсоткове число (`5` = 5%); `max_round_trip_cost_pct` також задається у відсотках (`0.5` = 0.5% повного entry notional), строго більше 0 і менше 100, без default. Max pairs 1–3, daily loss у % строго нижче 100; per-pair і aggregate notional мають спільну одиницю й aggregate ≥ per-pair. Invalid/incomplete → 422 без запису; невідомий бот → 404. Успішний PUT додає незмінну версію з UTC і deployment `config_version`, але завжди лишає `live_allowed=false`. Старий JSON draft без нового поля читається, але не проходить S24 cost preview; Paper `/bots/{id}/start` не читає цей draft. Endpoint не приймає mode, ключі чи ордери.

## Локальні exchange credentials (2026-10-21)

`POST /api/v1/exchange-credentials` приймає `{exchange:"mexc_futures",label,api_key,api_secret}`; `GET /api/v1/exchange-credentials` і `GET /api/v1/exchange-credentials/{id}` повертають тільки метадані та `api_key_masked`. `PUT /api/v1/exchange-credentials/{id}/rotate` приймає `{api_key,api_secret,expected_version}`; `POST /api/v1/exchange-credentials/{id}/revoke` незворотно прибирає поточний encrypted material. `GET/PUT /api/v1/bots/{id}/live-credential` читає/додає чергову immutable версію вибору; PUT приймає `{credential_id,expected_version}` (`null` для першого вибору) і лише active/supported credential. Ротація робить стару pinned version недійсною до нового PUT. Усі шляхи вимагають backend Bearer token, повертають `Cache-Control: no-store`, ніколи не віддають secret чи master key і завжди `live_allowed=false`. Missing/invalid/wrong vault key → 503 `CREDENTIAL_VAULT_UNAVAILABLE`; stale expected version → 409. Відкликання або відсутній вибір не активує Live. API не здійснює приватний MEXC GET чи брокерський виклик.
