# Інтеграція MEXC Futures

Це план адаптера, а не підтверджений перелік endpoint-ів. Перед реалізацією знайти й перевірити чинну офіційну документацію MEXC Futures та умови доступу, зафіксувати конкретні URL, поля, ліміти, часові правила й дату перевірки. Якщо певний тип даних недоступний, UI й симулятор мають явно показати обмеження.

## Дані для MVP

| Дані | Використання | Поведінка при відсутності |
|---|---|---|
| Каталог контрактів і правила інструментів | precision, tick/lot size, min/max, статус торгів | Заборонити нові ордери для інструмента |
| Trades/ticker і bid/ask | живі ціни, spread, оцінка fills | Позначити дані stale, блокувати нові входи |
| OHLCV за вибраними таймфреймами | графік, індикатори, стратегії | Не генерувати сигнал на неповній свічці |
| Глибина книги, якщо доступна | модель ліквідності й прослизання | Перейти до позначеної консервативної моделі, не називати її точною |
| Funding rate та розклад, якщо доступні | paper/backtest funding | Не домислювати історичні нарахування; показати пропуск |
| Open interest, якщо доступний | додатковий контекст AI/аналітики | Поле nullable, стратегія має оголосити потребу |

## Контракт нормалізації

Кожен event має `exchange`, `instrument_id`, `event_type`, `source_time_utc`, `received_at_utc`, `sequence_or_cursor` (якщо є), `payload`, `quality_status` і `raw_ref`. Інструмент має канонічний ID, quote/settle asset, тип контракту та точності. Числа — decimal strings на межі API. Свічка стає фінальною тільки за надійним прапорцем джерела або після закінчення інтервалу з контрольним запитом.

## Синхронізація і відмови

1. При старті отримати snapshot і статус інструмента, синхронізувати часову різницю, потім підписатися на WS.
2. Обробляти WS-події за sequence/time згідно з офіційним контрактом; дублікати відкидати, gap фіксувати і закривати snapshot-запитом.
3. Встановити deadline актуальності за типом даних і таймфреймом; значення визначити та протестувати після вимірювання реального потоку. До цього використовувати консервативний блок нових входів при втраті зв'язку.
4. Reconnect із backoff/jitter і дотриманням актуальних rate limits; не переповнювати API запитами після збою.
5. Записувати метрики затримки, втрат, reconnect, HTTP 429/5xx і невідповідностей snapshot/stream.

## Торговий API — тільки майбутній Live

Секретний адаптер окремий від public data. Перед Live перевірити scopes ключа, підпис/час, idempotency, типи ордерів, reduce-only, hedge/one-way, isolated/cross, partial fills, cancel/replace, reconciliation, обмеження символів і правила API. Ніякі приватні ключі не потрібні для Paper Trading. Якщо біржа не підтримує потрібну гарантію, Live gate залишається закритим.

## Приймання адаптера

Під час Market Data етапу: зафіксована матриця endpoint/stream з посиланням на офіційні джерела; живий BTC/USDT відображається з часом джерела та станом якості; тест розриву/повтору/gap не породжує хибної свічки або сигналу; працює без приватного ключа, якщо публічний доступ підтверджений.
