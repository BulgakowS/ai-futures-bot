# Локальне сховище біржових credentials: дизайн 2026-10-21

Мета цього етапу — зберігати кілька credentials та вибирати один для чернетки конкретного бота. Це не Live gate, не перевірка прав на біржі й не шлях виконання ордерів. Введення підтримує лише `mexc_futures`; `exchange` залишається явним discriminator для окремого майбутнього рішення про інші біржі.

Розглядали три варіанти: окремі env-змінні для кожного акаунта (секрети не в БД, але незручно версіонувати вибір бота), plaintext у БД (простий UI, неприйнятний витік через БД/backup), зашифрований material у БД із master key лише в локальному секреті. Обрано третій варіант: AES-256-GCM із новим 96-bit nonce на кожне створення/ротацію, AAD з ID, exchange і версією. API не має маршруту розшифрування. Master key — 32 bytes у URL-safe base64, створений `make setup` у ignored `.env.credentials` mode 0600, переданий тільки контейнеру API. Відсутній, некоректний або невідповідний ключ дає 503; жоден active запис не читається чи змінюється. Втрата ключа означає втрату можливості відновити material із backup; його треба зберігати окремо від backup БД. Операційної ротації master key цей етап не реалізує.

`exchange_credential` має UUID, exchange, label, 4-символьний masked hint, nonce/ciphertext, version, active/revoked, UTC timestamps та config version. У ciphertext лише JSON `api_key/api_secret`. Ротація замінює ciphertext і підвищує версію; revoke очищує поточні nonce/ciphertext/hint і незворотний через API. Старі WAL, snapshots або backups можуть містити попередній ciphertext і потребують окремої політики retention/шифрування; фізичне стирання з них не заявляється. `bot_credential_selection` — append-only `(bot_id,version)` із credential ID та pinned credential version. Після ротації/revoke вибір недійсний до нового явного PUT; Paper bot mode, config, ledger і scheduler його не читають.

Authenticated API: `POST/GET /api/v1/exchange-credentials`, `GET /{id}`, `PUT /{id}/rotate`, `POST /{id}/revoke`, `GET/PUT /api/v1/bots/{id}/live-credential`. У відповідях лише label, masked hint, стан, версії й `live_allowed=false`. PUT binding приймає `expected_version` для захисту від застарілого вибору, перевіряє active/supported credential; rotation має `expected_version`. На всіх цих шляхах `Cache-Control: no-store`, включно з помилками. Валідаційні помилки не відлунюють введені секрети.

Межа загроз: backend bearer token наразі локальний спільний секрет, а не per-user auth; UI BFF має пропускати тільки явно дозволені маршрути та чинний origin/host gate. Browser не отримує master key або повний credential material, але той, хто контролює локальний браузер із доступом до BFF, може створити/відкликати credential. Компрометація API процесу чи його master key дозволить розшифрування; шифрування at-rest захищає насамперед дамп БД/backup без ключа. Live runtime та приватні MEXC виклики не додані.
