# S11/G1 — GDELT aggregate forward source contract

Дата перевірки офіційних сторінок: **2026-10-18, 10:14–10:17 UTC**; попередній [N0b аудит](evidence/s11-n0b-alternative-news-sources-2026-10-18.md). [GDELT Terms of Use](https://gdeltproject.org/about.html#termsofuse) дозволяють необмежене безоплатне academic/commercial/governmental використання **GDELT datasets**; redistribution/rehosting потребують citation GDELT і посилання на його сайт. [GDELT Data](https://gdeltproject.org/data.html) описує modeling/forecasting на datasets. **Внутрішнє source eligibility decision:** власні агреговані числові поля GDELT `date`/`value` придатні для локального дослідницького modeling за цим контрактом; додатковий письмовий дозвіл не є gate. Це рішення не поширюється на title, URL чи full text сторонніх видань. У будь-якій публікації результатів зазначати “Data source: GDELT Project” із посиланням на `https://gdeltproject.org/`. G1 нічого не тренує, оскільки GDELT-compatible dataset/feature і frozen artifacts ще не створені.

Перший дозволений payload — публічний GDELT DOC API `GET https://api.gdeltproject.org/api/v2/doc/doc?query=bitcoin&mode=timelinevol&format=json&timespan=1d`. Зберігаємо тільки єдину серію `Volume Intensity`: UTC `date` з кроком 15 хв і Decimal `value` як **GDELT aggregate intensity**, не як кількість статей чи ціновий сигнал. Метадані `query_details.title=bitcoin` і `date_resolution=15m` використовуємо лише для перевірки схеми. `article title`, `URL`, `full text`, publisher metadata, raw HTTP body і сторонні snippets не зберігаються. Невідомі поля/серії призводять до відмови без часткового ingest. Не робимо backfill чи article-list запитів. Перший bounded public probe 2026-10-18 дав 52 точки, 25 ненульових; це перевірка формату, не доказ повноти, стабільності API чи придатності до прогнозу. Raw проба лишається тільки в локальному `/tmp/ai-futures-gdelt-probe.json`.

Один ручний виклик `scripts/poll_gdelt_once.py` потребує `GDELT_FORWARD_ENABLED=true`; немає scheduler, API POST або зв'язку з торговим контуром. За виклик дозволено щонайбільше один GET із timeout 8 с, body ≤256 KiB, ≤96 точок і без redirect/retry. Повтор раніше 15 хвилин пропускається. 429, 5xx, transport/schema/body error дають append-only `error` scan із кодом без точок. Успішна відповідь створює append-only numeric revisions за UTC bucket: `first_seen_at` фіксується локально при першому спостереженні, `observed_at` при ревізії; стара версія не змінюється. Availability для дослідження: `max(point_at, first_seen_at)`; корекція доступна лише з її власного `observed_at`. У межах ковзних 96 слотів відсутній bucket є **unknown**, ніколи нулем; coverage scan `gap`, доки немає всіх слотів. Є causal `scan_id`, UTC, source/config version. PostgreSQL/SQLite UPDATE і DELETE блокуються тригерами.

MEXC `BTC_USDT` public market і 4h horizon лишаються цільовими, але GDELT агрегат **не під'єднаний** до старих `AnnouncementVersion`, `news_dataset`, `news_training`, `ModelBotService`, Paper або Live. Старий MEXC announcement шлях залишається test-only; права на MEXC news не встановлено. Перед N2b/N3b потрібні окремі source-compatible dataset/feature контракти, перевірка реального forward coverage, часу доступності й відповідності GDELT агрегату задачі. N5 gate та окреме рішення про активацію автоматичних лише Paper угод лишаються відкритими.

## G2 — offline event-time dataset contract (2026-10-18)

Окремий `gdelt_dataset.py` працює тільки з копіями G1 `GdeltVolumeRevision`, `GdeltVolumeScan` та `Candle` (`payload["close"]` мапиться на `MarketCandle.close`). DTO поля відповідають persisted полям; `revision_id`, `scan_id`, `event_id` у DTO подаються рядками, а `close`/`value` — десятковими рядками. Експортер із БД, його транзакційний snapshot і concurrency ще не реалізовані. Синтетичний builder не читає БД/мережу, не тренує модель і не створює торгових рішень.

`DatasetConfig.first_anchor..last_anchor` фіксує всі UTC 4h anchors наперед. На кожний anchor builder повертає рівно один sample або `WAIT`, навіть якщо market чи aggregate дані відсутні. Ознаки беруть дві завершені `BTC_USDT` 4h свічки та всі 16 GDELT 15-хвилинних слотів `[anchor−4h, anchor)`. Для кожного слота береться остання ревізія з `observed_at <= anchor`, причому її `first_seen_at` і `available_at=max(point_at,first_seen_at)` також не можуть бути пізніші за anchor. Ревізія після anchor не змінює минулі ознаки; ревізія вже в поточному вікні дає `WAIT volume_revision_conflict`. Значення `0` є валідним, відсутній слот — `WAIT volume_slot_missing`, без заповнення нулем. Локальна затримка першого спостереження >30 хв дає `WAIT volume_slot_late`.

Потрібен останній scan `<=anchor` зі статусом `ok`, без missing buckets і віком ≤30 хв. `gap`, `error`, sparse або stale coverage дають `WAIT`; сам статус `ok` не замінює перевірки 16 слотів. Market candle з `source_time`/`received_at > anchor`, nonfinal або відсутня дає `WAIT`, оскільки mutable `Candle` не зберігає історії корекцій. Майбутня фінальна 4h candle використовується **лише** для label через Decimal cost threshold, після дозрівання `anchor+4h`; вона не входить в ознаки. Вихід має окремі market-only/aggregate/full feature hashes, IDs і payload hashes, source/config versions та source/config/dataset SHA-256 checksums. Chronological split має симетричне embargo ≥4h. Це frozen offline snapshot contract, не provenance attestation реального джерела.

**Source viability blocker:** єдина bounded 1d real DOC проба G1 дала 52/96 можливих слотів. За чинним strict coverage G2 такі anchors отримають `WAIT`; немає доказу, що GDELT API може дати 95% as-of coverage у потрібному режимі. Окрема 4h probe завершилася timeout і не встановила семантики/частоти series. Не послаблювати coverage або не домислювати відсутні точки без офіційно перевіреної семантики API та реального forward журналу. Stage 9 і N5a залишаються `collect-only`.

Операційна перевірка [офіційного опису DOC 2.0, секція MODE](https://blog.gdeltproject.org/gdelt-doc-2-0-api-debuts/) через gstack `/browse` 2026-10-18 близько 19:43 UTC уточнила: `TimelineVol` є відсотком усіх monitored online articles у timestep; для інтервалів <72h timestep 15 хв. `TimelineVolRaw` повертає distinct matched article count та `norm` total monitored articles. G1/G2 лишаються на `TimelineVol` і трактують `value` як intensity, не article count. Документація не гарантує заповнення всіх 96 слотів; опис timestep не пояснює фактичні 52/96. Другий bounded `timelinevolraw/1d` API probe отримав HTTP 429, попередній 4h probe — timeout. Не підміняти G1 source режимом Raw і не робити нових probes без окремого плану; operational source viability залишається відкритою.

## G0d — GKG release stream як окремий кандидат (2026-10-18)

[Один bounded read-only GKG 2.1 release](evidence/s11-g0d-gkg-release-2026-10-18.md) із `lastupdate.txt` пройшов size/MD5 manifest check: 3,313,906-byte ZIP, 732 TSV рядки по 27 codebook полів, один `V1THEMES=ECON_BITCOIN` row і валідний `V1.5TONE`. Це доводить лише можливість обчислити власні GDELT-derived **BTC theme row count і mean document tone** за одним 15m batch. Ці поля мають іншу семантику, ніж DOC `Volume Intensity`; один batch не доводить сталого release coverage чи достатньої кількості BTC спостережень. Оціночний трафік за незмінного розміру — 303.4 MiB/day. Для GKG candidate дотримуватися того самого обмеження прав: лише числові GDELT-derived aggregates/coverage, без article title/URL/full text/quotes/publisher metadata/raw archive у DB чи repo.

Потенційний GKG source v2 потребує окремого versioned schema/event-time контракту та bounded forward перевірки очікуваних 15m release IDs, `first_seen_at`, lag, gaps, corrections, zero-vs-missing і bandwidth. Відсутній release лишається `unknown`; пізня ревізія не переписує минулий anchor. До такого рішення Stage 9 — `collect-only`.

## G3 — bounded GKG candidate forward journal (2026-10-18)

Після G0d одноразовий collector реалізовано **окремо** від G1/G2/N5a. Офіційні джерела GKG/Data/Terms/codebook і дата їх перевірки зафіксовані в [G0d evidence](evidence/s11-g0d-gkg-release-2026-10-18.md); G3 не виконував нового реального HTTP запиту. Ручний `scripts/poll_gkg_once.py` потребує `GKG_FORWARD_ENABLED=true`, за замовчуванням вимкнений, не має scheduler/API route або модельного/Paper wiring. Одна спроба: лише `GET https://data.gdeltproject.org/gdeltv2/lastupdate.txt` і максимум один GET останнього `YYYYMMDDHHMMSS.gkg.csv.zip` на тому самому host/path; URL у manifest нормалізується до HTTPS. Немає redirects/retries. Кожний GET має 15 s загальний deadline; manifest ≤4096 B, ZIP ≤8 MiB, розпакований один CSV ≤30 MiB. Наступна спроба раніше 15 хвилин пропускається. Batch ID перевіряється як UTC 15m, не майбутній понад 15 хв і не старший за 2 години від локального scan time; зворотний рух ID та стрибок понад 96 слотів відхиляються. Немає corpus backfill.

Manifest має рівно один GKG entry із decimal ZIP size і MD5. Size та MD5 перевіряються перед розбором; SHA-256 ZIP зберігається як локальний payload hash, не видається за manifest-verified hash. ZIP повинен мати рівно один `<batch>.gkg.csv`; кожний рядок — рівно 27 tab колонок, `V2.1DATE` (поле 2) тотожна batch ID, `V1.5TONE` (поле 16) — сім скінченних Decimal із захисним лімітом 64 цифри й absolute adjusted exponent ≤30. `ECON_BITCOIN` рахується як точний `;`-токен поля 8. Зберігаються лише `total_rows`, `btc_rows` та mean першого tone компонента **в BTC subset**; при успішному release без BTC рядків `btc_rows=0`, mean=`NULL`. При відмові немає aggregate revision, навіть нульової.

`gkg_scan`, `gkg_slot_observation`, `gkg_release_revision` — окремі append-only таблиці з UTC, causal `scan_id`, source/config version. Scan містить status `ok|repeat|error`, bounded error code та отримані bytes. Slot observations позначають `ok|repeat|error|unknown` для видимих/очікуваних 15m ID; відсутність та помилка не означають нуль. Локальний `first_seen_at` береться після успішного отримання й розбору ZIP; доступність release для майбутнього дослідження — `max(batch_at,first_seen_at)`. Пізні ревізії того самого ID мають окремий `observed_at`, immutable sequence та SHA-256 і не змінюють попередній as-of зріз. Тотожний manifest повторно не завантажує ZIP; це не виявляє silent correction без зміни size/MD5. Якщо немає попереднього scan, collector не вигадує попередню історію слотів; після >96 послідовних невідомих слотів scan отримує `gap_limit` замість необмеженого запису.

Тільки власні числові GDELT-derived aggregates/coverage потрапляють у БД. Сирий ZIP, article URL/title/text, publisher metadata, цитати й інші поля відкидаються в пам'яті. Дані GKG мають іншу семантику, ніж DOC `Volume Intensity`; до реального тривалого forward coverage/latency/bandwidth і окремого source v2 dataset/protocol рішення G1/G2/N5a не змінюються, Stage 9 — `collect-only`. Один G0d release та mock G3 тести не є доказом придатності чи predictive lift.

## G4 — окремий числовий GKG 4h dataset і test-only export (2026-10-18)

`gdelt_gkg_dataset.py` має незалежну схему `gdelt-gkg-market-dataset-v1` для G3 `gdelt-gkg-econ-bitcoin-candidate-v1`; вона не переіменовує G1/G2 DOC `Volume Intensity`. На кожен заздалегідь заданий UTC 4h anchor повертається sample або `WAIT`. Для ознак потрібні дві фінальні MEXC `BTC_USDT` 4h Candle та рівно 16 GKG batch ID у `[anchor−4h, anchor)`. Для кожного batch беруться лише release/slot observations із `observed_at ≤ anchor`; `available_at=max(batch_at,first_seen_at) ≤ anchor`, а lag першого спостереження ≤30 хв. Відсутність, `unknown`/`error`, запізнення, ревізія до anchor, конфлікт observation або market correction/nonfinal дають `WAIT`. Ревізія після anchor не змінює його features. `btc_rows=0` допустимий лише з валідного release `total_rows>0`; при сумі нуль tone=`NULL` та `tone_missing=true`.

Версійовані числові ознаки: market return у bps, сума BTC theme rows, сума всіх GKG rows, `BTC/total` share та зважений за BTC rows mean document tone. Останній не є BTC-specific sentiment. Окремі market/aggregate/full SHA-256 hashes не містять future candle; `UP|DOWN|NEUTRAL` label використовує лише наступну фінальну 4h Candle і Decimal `cost_bps` із `cost_version` після `anchor+4h`. Dataset має immutable UTC provenance IDs, source/config versions, config/source/dataset checksums; chronological split вимагає embargo ≥4h. Portable seal перевіряє `verify_dataset()`.

`gdelt_gkg_export.py` копіює лише обмежені потрібним вікном G3 revision/slot/scan та Candle rows (≤8192 на таблицю) з однієї явної SQLite read transaction. Запуск дозволений тільки `APP_ENV=test` і SQLite файлом у системному тимчасовому каталозі; active PostgreSQL/Compose не читається. Це offline research snapshot, без train/inference/Paper/Live wiring. Один реальний одноразовий G3 poll у disposable test SQLite дав release `20261018200000`: `first_seen_at=19:56:45 UTC`, 688 total rows, 2 BTC rows, 3,042,368 ZIP bytes. Availability цього batch — **20:00 UTC**, і один release не доводить 16-slot coverage чи придатності cohort. [G4 evidence](evidence/s11-g4-gkg-dataset-2026-10-18.json). Stage 9 лишається `collect-only` до репрезентативного forward coverage, market/cost source verification і окремого N5-compatible protocol/gate.

**Межа market provenance для старого G4 export:** mutable `Candle` не зберігає попередню версію. S11/M1 нижче переводить **лише GKG persisted export** на окремий append-only market journal; старі mutable-only anchors та G1/G2/N2b не отримують історичної attestation заднім числом.

### G4/T1 — event-time amendment перед training (2026-10-18)

G4 dataset schema піднято до `gdelt-gkg-market-dataset-v2`: `anchor` є **номінальним закриттям** поточної MEXC 4h Candle, а `decision_at` — найранішим UTC моментом, коли ця фінальна Candle і всі 16 валідних GKG release/slot observations уже доступні. Затримка від anchor обмежена `Config.max_decision_delay` (default і maximum 15 хвилин). Поточна Candle з `source_time` або `received_at` після межі дає `WAIT market_late_or_corrected`; відсутній до межі GKG слот дає `WAIT release_slot_missing`, `unknown`/`error` — `WAIT release_slot_unknown`. Попередня Candle мусить бути відома до anchor. Обираються лише ревізії/спостереження, scan timestamps і market records з часом доступності `<=decision_at`; ревізії після рішення не переписують його. Якщо будь-яке джерело виправлено до рішення, чинний conflict gate лишається `WAIT`. `cutoff` також не дозволяє рішення раніше фактичної доступності.

Sample тепер містить `decision_at`, `target_close_at=anchor+4h` та точний Decimal text `time_to_target_seconds`; `decision_at` входить до обох feature hashes і sealed dataset manifest. Первинний T1 test-only export мав manifest schema `persisted-gkg-market-export-v2`; M1 нижче підняв persisted export до v3. `UP|DOWN|NEUTRAL` порівнює **close поточної 4h Candle з close наступної 4h Candle** після появи фінального label. Це next-4h-close target на номінальній сітці, а не точний 4h прогноз або дохід від ціни виконання в `decision_at`; фактичний час до target становить від 3h45m до 4h. Future candle жодним чином не входить до features. Старі v1 snapshots/artifacts не сумісні з v2 і не використовуються для training/forward без нового freeze. GKG усе ще candidate `collect-only`; 15m межа є policy, а не виміряний розподіл реальної MEXC/GKG latency.

## G6 — explicit bounded research pilot CLI (2026-10-19)

`scripts/pilot_gkg_forward.py` запускається лише з `APP_ENV=test`, `GKG_PILOT_ENABLED=true` та `GKG_FORWARD_ENABLED=true`. Він сам створює новий SQLite файл у системному temp, мігрує тільки його й зберігає після завершення або Ctrl-C. Запуск із кореня репозиторію: `APP_ENV=test GKG_PILOT_ENABLED=true GKG_FORWARD_ENABLED=true PYTHONPATH=.:services/api .venv/bin/python scripts/pilot_gkg_forward.py`. Це окремий ручний 4h15m research run, а не production scheduler; active PostgreSQL/Compose, Paper, inference і trading modules не відкриваються.

Ліміти: максимум 18 спроб; monotonic pacing ≥15 хв між початками; остання спроба стартує тільки якщо до кінця 4h15m вікна лишається ≥60 с. Кожний poll зберігає G3 обмеження 15 с на GET, ≤4096 B manifest, ≤8 MiB ZIP, ≤30 MiB розпакований TSV, без redirect/retry/backfill. Додатковий test-only download budget до poller блокує ZIP GET, якщо manifest bytes плюс заявлений ZIP size перевищать залишок загального ліміту 128 MiB; це append-only `download_budget` error і негайне завершення. Будь-які 429, transport/schema/error або несподіваний throttle зупиняють цикл. SIGINT/SIGTERM завершує поточний обмежений poll, фіксує scan та припиняє наступні спроби.

Вивід — лише JSON рядки зі status, UTC, batch ID, revision, scan/release/slot counts, unknown gaps, first-seen lag і byte totals; немає raw GKG, article metadata, ZIP, body, URL із manifest чи секретів. При setup failure друкується тільки сталий код. Новий файл SQLite залишається research journal для read-only аналізу. На момент підготовки G6 пілот ще не запускався; два старі реальні contiguous batch `20261018200000` і `20261018201500` у `/tmp/ai-futures-gkg-forward-20261018.sqlite` не доводять повної 16-slot cohort. Навіть успішний пілот не підтвердить market/cost provenance, репрезентативність або predictive lift; Stage 9 лишається `collect-only`.

### G6a — DB UTC pacing після часткового пілоту (2026-10-19)

Перший явний real pilot дав успішні спроби о 07:00:28 та 07:15:29 UTC, потім о 07:30:29 повернув `throttled` без HTTP/scan і зупинився з двома release та двома `ok` slots. Причина: runner чекав 900 с за monotonic clock від моменту **до** виклику, а G3 зберігав `attempted_at` за UTC трохи пізніше. На межі різниця в мікросекундах/мілісекундах порушувала G3 throttle. G6a читає останній persisted `gkg_scan.attempted_at` перед кожною спробою і чекає одночасно до UTC `attempted_at+15m` та monotonic `last_start+15m`; новий GET до обох меж неможливий. Вікно 4h15m, 18 спроб і 128 MiB aggregate transfer cap залишилися. Якщо зовнішній writer змінив DB після перевірки, несподіваний throttle лишається fail-closed без retry. Після G6a real pilot не запускався; два `ok` slots не є 16-slot cohort.

## S11/M1 — immutable Hour4 market provenance, 2026-10-19

`MARKET_CANDLE_JOURNAL_ENABLED=false` за замовчуванням. Після окремої міграції `d3c7a5e91f02` явне ввімкнення додає REST `Hour4` до market refresh (кожні 30 с за наявного WS; також при reconcile). Кожна фінальна `BTC_USDT` 4h REST reconciliation атомарно з чинним mutable `Candle` додає `MarketCandleObservation`: UTC `first_seen_at` першої версії, UTC `observed_at` поточної, `source_time` як оцінку біржового server clock під час REST response (сам candle endpoint окремого update timestamp не дає), SHA-256 payload, Decimal-text close, `source=rest`, source/config/rules versions, causal UUID та номер версії. Ідентичний payload після рестарту не створює row; зміна й повернення попереднього payload утворюють нові версії. WS/provisional і інші таймфрейми не журналюються. Journal failure відкочує той самий Candle write; broker не викликається. До міграції прапорець лишається off, тож поточний Paper ingest читає/пише лише `Candle`.

GKG persisted export v3 читає лише immutable `MarketCandleObservation` в одній bounded disposable SQLite snapshot. При вимкненому flag або відсутніх спостереженнях кожен anchor має `WAIT market_gap`, навіть коли mutable `Candle` існує. Для ознак фіксується версія, доступна на фактичний `decision_at`; correction **до** рішення дає `WAIT market_revision_conflict`, correction **після** рішення не змінює його feature hash. Label бере наступну фінальну версію, доступну до export `cutoff`, і не входить в ознаки. Export seal v3 включає IDs/versions/rules/source для всіх прочитаних market observations. Старі v2 persisted seals не приймаються як real GKG eligibility. Потрібні окремі перевірки довгого Hour4 coverage, ліміту/пропусків і actual rules/cost provenance; міграцію на active PostgreSQL/Compose та production flag у M1 не застосовували.

## S11/M2a — public rules journal і сценарні витрати, 2026-10-19

## S11/G7a — sparse GKG source v3, bounded one-shot collector (2026-10-19)

Окремий `gdelt-gkg-sparse-v3` є низькотрафіковим **candidate** і не підміняє G3 `gdelt-gkg-econ-bitcoin-candidate-v1`, G4/G5b 16-slot dataset або N5b. [Бюджетний outline](plans/2026-10-19-s11-g7a-sparse-gkg-v3-outline.md) визначає один заздалегідь заданий `anchor−15m` GKG batch на кожен UTC 4h anchor. Ручний `scripts/poll_gkg_sparse_once.py` вимагає `APP_ENV=test`, `GKG_SPARSE_ENABLED=true`, існуючий мігрований SQLite файл `data/research/s11-gkg-sparse.sqlite` й явний `--anchor`; CLI не приймає іншого journal path. Тимчасові SQLite дозволені лише з mock HTTP в тестах. Без opt-in немає HTTP; scheduler/API/Paper/inference не підключені. G7a real GET не виконували.

Після anchor і не пізніше `anchor+15m` collector атомарно записує immutable claim на 8,470,528 B. SQLite `BEGIN IMMEDIATE` і unique anchor не допускають паралельний або повторний GET; після crash claim без outcome залишається `unknown` і резерв не повертається. Один HEAD перевіряє `200`, `Content-Length` у `(0,8 MiB]`; один GET того самого fixed HTTPS URL перевіряє status, той самий length, identity encoding та рівно оголошену кількість ZIP bytes. Redirect/retry/backfill немає; 15 s deadline, ≤8 MiB ZIP, G3 strict parser із ≤30 MiB TSV/27 полями/Decimal tone. Зберігаються лише aggregate count/mean, ZIP SHA-256, UTC `first_seen_at`, source/config/causal IDs, статус/error та облік bytes. Сирий ZIP, article/title/URL/text не пишуться. Валідний BTC zero відрізняється від missing/error.

Append-only budget journal має жорстку межу 5,000,000,000 B, відкривальний debit 134,217,728 B (22,384,251 B відомих ZIP + 434,652 B codebook PDF + 2,486 B DOC JSON + 319 B manifest + 111,396,020 B резерв на решту старого трафіку) і суму незворотних claims. Якщо наступний claim перевищить cap, HTTP не починається. Локальні файли звірено, але exact total усіх старих вебвідповідей не журналювався; debit лишається консервативним припущенням. Інші news collectors треба зупинити, бо їхні запити не входять у цей ledger. Розміри HTTP framing/TLS у локальному `response_bytes` не вимірюються. 56 діб × 6 anchors = 336 batch і 2,846,097,408 B maximum claims, але статистична придатність такого sparse signal невідома. [Sanitized evidence](evidence/s11-g7a-sparse-gkg-2026-10-19.json).

Ручний запуск вимагає **один збережений** SQLite журнал `data/research/s11-gkg-sparse.sqlite`, вже мігрований до head; не видаляти його й не створювати нову DB для кожного anchor. `--anchor` — ISO 8601 UTC з точним 4h boundary. Синтаксис наступного запуску: `APP_ENV=test GKG_SPARSE_ENABLED=true PYTHONPATH=.:services/api .venv/bin/python scripts/poll_gkg_sparse_once.py --anchor 2026-10-19T16:00:00Z` (приклад має сенс лише у вікні 16:00–16:15 UTC). Якщо процес падає після claim, жодна команда не відновлює GET для цього anchor. До нового source-compatible dataset/protocol, bounded real coverage/latency, market/rules/cost provenance та frozen artifacts Stage 9 лишається `collect-only`.
