# UX-специфікація

## Принципи

Перший екран відповідає на три питання: чи актуальні дані, що робить бот, який зараз ризик. Детальні налаштування відкриваються поступово. Числа про результат відрізняють realized/unrealized, кошти/відсотки, paper/live/backtest і точні/оцінені дані. Ніде не створювати враження гарантованої дохідності.

## Навігація

| Екран | Основний вміст | Основна дія |
|---|---|---|
| Dashboard | стан підключення, equity, PnL, експозиція, активні боти, останні рішення | перейти до проблеми/бота |

| Bots | список, стан, стратегія, портфель, результат, wizard | створити/запустити/призупинити |
| Positions | відкриті позиції, маржа, mark, SL/TP, ризик | переглянути/закрити через risk gate |
| Analytics | equity curve, drawdown, витрати, порівняння, journal | фільтр/експорт |
| Settings | ринки, профілі ризику, AI, API-секрети, повідомлення, мова | зберегти версію конфігурації |

Dashboard показує окремий список **усіх Paper ботів** (включно з DRAFT/PAUSED/STOPPED), сформований із ботів, а не всіх портфелів. Для кожного: назва пов'язаного портфеля, статус, номер поточної епохи, депозит, чистий реалізований PnL після проведених fees/funding, нереалізований PnL та чистий загальний PnL у USDT зі знаком і словесним прибуток/збиток/без змін. Після reset результат починається з нового депозиту; попередня епоха лишається в журналі. За невідомої valuation загальний і нереалізований результати показуються як `—` разом із `DATA_STALE` або `FUNDING_UNRESOLVED`; проведений реалізований результат лишається видимим. Є переходи до картки бота й ledger журналу його портфеля, а також loading/empty/error стани і UA/EN підписи на mobile.

## Майстер бота

1. Обрати режим Paper (дефолт), портфель/стартовий баланс, інструмент і таймфрейм.
2. Обрати стратегію та пресет; показати просте пояснення й параметри.
3. Обрати risk profile. Показати максимальні обмеження; небезпечні або неможливі значення блокувати до збереження.
4. Додатково ввімкнути AI та ліміт витрат, якщо є ключ.
5. Екран перевірки показує припущення симуляції, реальність котирувань, віртуальність ордерів, версії конфігурацій. Запуск створює окремий екземпляр бота.

`Simple` показує рекомендовані профілі й ключові параметри; `Advanced` — індикатори, SL/TP, частоту; `Expert` — усі доступні контракти конфігурації та попередження. Перемикання рівня не змінює збережені значення непомітно.

У поточному Paper UI `Простий · модель` створює лише `DRAFT` із назвою, віртуальним депозитом, лімітом повного notional однієї позиції в USDT (включно з плечем), явним плечем 1–3× і верхніми межами відсоткової відстані SL/TP від ціни входу. Збережені `stop_loss_pct` і `take_profit_pct` — саме межі; після окремого схвалення модель зможе вибрати точні `0 < distance_pct ≤ cap` для кожного рівня, а не зобов'язана використати cap. Фактичний збиток може перевищити SL через прослизання, а досягнення TP не гарантує fill. Ліміт позиції — повна вартість з обраним плечем, не маржа; плече не збільшує цей ліміт. Поле плеча обов'язкове, його діапазон перевіряють UI і backend, а картка показує збережене значення та обидві відсоткові межі. Без real forward promotion моделі картка показує `MODEL_NOT_APPROVED` і не пропонує `ready/start`; backend і worker теж блокують виконання. `Ручне налаштування` лишає чинну форму rule-based бота. Поруч із лейблами всіх полів цих форм і чернетки Live pilot є UA/EN іконка з поясненням при hover/focus; вона не змінює значення поля. Цей частковий Simple режим не є перевіреним торговим пресетом і не закриває повне приймання Simple/Advanced/Expert.

У секції **Налаштування → Біржові підключення** локальний користувач бачить тільки назву, `MEXC Futures`, маску API key, версію й стан кожного запису. Окрема форма приймає `api_key` і `api_secret` лише при створенні або заміні; після успіху ці поля очищуються, API більше не повертає secret. Є дії заміни та відкликання з явним підтвердженням останнього. Недоступний vault має власний стан помилки й кнопку повтору. У картці кожного бота дія **Підключення для майбутнього Live** відкриває вибір тільки активних MEXC Futures записів і показує застарілу прив'язку після ротації/відкликання; вибір зберігається окремою версією. UA/EN і 375 px підтримуються. Весь потік є чернеткою: Paper worker не читає credentials, а Live ордери лишаються вимкненими. Інші біржі потребують окремого адаптера та перевірки перед появою в selector.

## Графік і журнал

Графік Lightweight Charts показує фінальні свічки, позначки входів/fills/виходів, SL/TP і вибраний таймфрейм. Для кожної позначки можна відкрити «чому»: snapshot часу, сигнал/AI, risk verdict, fill, fees, funding та PnL. Якщо дані застаріли, банер показує останній час джерела; кнопка запуску нових входів недоступна з поясненням.

## Стани й доступність

Усі асинхронні екрани мають loading, empty, error і degraded стани. Режим, середовище й валюта показані біля балансу. Kill switch постійно доступний під час роботи ботів, має підтвердження наслідків і видимий статус після дії. Клавіатурна навігація, достатній контраст, підписи для кольору прибутку/збитку, локалізовані UA/EN тексти. Mobile layout зберігає критичні дії та стан ризику без горизонтального прокручування.

Для Paper Overview структурований `GET /health` зі статусом HTTP 503, `status=degraded`, `mode=paper` і переліком `dependencies` є станом деградації, а не помилкою завантаження сторінки. Банер показує несправну залежність, коли ринкові дані ще актуальні; при застарілому ринку першою показується його причина. Недоступний BFF або інша неструктурована 503 лишається помилкою з повтором. Запуск бота доступний тільки після успішного оновлення, `health=ok` і придатних ринкових даних; серверний Risk Engine перевіряє намір окремо.

## Майбутній Live

Live не з'являється як активна опція до проходження окремого gate. Якщо його буде додано, інтерфейс повинен мати однозначне візуальне розрізнення, окремий баланс/журнал і багатокрокове підтвердження ризику. UI не може сам відкрити серверний gate.

## Фактичний S06 local paper UI

На `localhost:3030` є Dashboard із MEXC public fairPrice, source time, trade eligibility, станом сервісу, paper equity/available/unrealized і графіком тільки REST-final OHLCV; Bots wizard явно показує кожен `StrategyConfig` та `RiskProfile` параметр, без готового торгового preset; `DRAFT/READY/RUNNING/PAUSED/STOPPED` дії, Positions із manual close через risk gate, журнал bot decisions, intent/risk/order/fill/ledger із provenance та fees, Settings kill switch, UA/EN і mobile layout. Оновлення HTTP snapshot кожні 8s. Якщо equity невідома через stale/funding, показується `—` і код valuation status. Fill та liquidation позначаються як оцінки. Збережений портфель вибирається після refresh.

Відкриті критерії етапу 5: Simple/Advanced/Expert, базова equity curve/drawdown аналітика, chart trade markers із переходом у причинний ланцюг, автоматичний UI тест нового bot fill/fees/SL/TP після сигналу, повний error/degraded стан для кожної вкладки. Початковий S06 графік — власний SVG для final OHLCV, а не цільова Lightweight Charts інтеграція; див. рішення P-11. Це не змінює джерело ринкових даних або правила risk gate.

S10C: у вкладці fill journal перед raw provenance явно показано «Оцінене виконання», public fee source/rate і, для limit, «перетин REST книги без черги». У provenance доступні rules/depth versions, обидві public ставки та застосована комісія. Pending passive limit не показується як maker fill.

S10F/F5b browser QA (2026-10-16): fill journal показує `estimated_fill`, застосовану public taker rate/source та скорочені rules/depth versions без потреби розкривати raw JSON. Для відкритої Paper позиції Positions показує `model_estimate`, tier і розкривне повне liquidation provenance (rules, mark, source, assumptions); для закритої позиції API явно повертає `unknown/POSITION_CLOSED`. За ширини 375 px Positions стає вертикальними картками: model provenance і кнопка close залишаються видимими, `document.scrollWidth=375`; у Journal також `scrollWidth=375`. Це перевірено через gstack `/browse` на `127.0.0.1:3000`, а не лише CSS inspection. Автономний bot signal у цьому QA не виник: виконані fills були окремими ручними Paper intent за чинними public snapshots, без synthetic market event в активній БД.

Залишилося UX-приймання degraded стану при короткому public `ticker_stale`: 2-секундний API sample його бачив, але browser не зафіксував банер/disabled дію саме в це вікно. Не вважати 31 хвилинний `quality=ok` sample доказом безперервної придатності до торгівлі.

## S11/N4b research view

Окрема вкладка «Дослідження / модель» показує `BTC_USDT / 4H / COLLECT-ONLY` і пояснює, що synthetic тести не доводять ринкової якості. Вона читає лише auth-protected forecast GET через BFF: останні записи, `WAIT` reason/quality, class scores та provenance (UTC, causal/model/dataset/config/source, market/news IDs). Кандидатні entry/SL/TP відображаються тільки для запису з явним `TEST · синтетичний fixture`; кнопки виконання немає. Порожній журнал пояснює, що real news-модель не запущена. Стан основного Paper UI не залежить від успіху research GET; помилка показується в research розділі.

## S21 налаштування чернетки Live pilot (2026-10-20)

У картці кожного Paper бота є окремий діалог «Ліміти майбутнього Live pilot» / «Future Live pilot limits». Він показує поточну версію й UTC час або стан unset, поля max 3 пари, per-pair/aggregate full notional, плече, TP/SL %, денну втрату; для сум можна вибрати USDT чи `% equity` (`5` = 5%). Жодне числове поле не має Live default. Підпис прямо каже, що Live вимкнений і збереження чернетки не дозволяє реальні ордери. Paper wizard і Paper start залишаються окремими; доступного Live mode toggle немає.
