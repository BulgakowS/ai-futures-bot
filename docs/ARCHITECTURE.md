# Архітектура

## Контекст

Система стартує як один репозиторій і локальний Docker Compose. Внутрішня логіка — модульний моноліт Python; API, довготривалий trading worker та AI worker можуть бути окремими процесами одного backend-коду. Frontend — Next.js. PostgreSQL зберігає стан і аудит, Redis допомагає з короткоживучими чергами та fan-out, але не є єдиним джерелом істини для ордерів чи балансу.

```text
MEXC public REST/WS -> Market Data -> normalized events -> Strategies / AI
                                              |                    |
                                              +------> Intent <----+
                                                         |
                                                    Risk Engine
                                                         |
                                              Paper Broker (MVP)
                                              Live Broker (disabled)
                                                         |
                                                Ledger + Journal -> API -> Web
                                                     |               |
                                                 PostgreSQL       Telegram
```

## Модулі й відповідальність

| Модуль | Вхід | Вихід | Межа відповідальності |
|---|---|---|---|
| Market Data | MEXC REST/WS | Нормалізовані tick/candle/book/funding; статус якості | Час, sequence, дедуплікація, gap detection, reconnect |
| Strategy Engine | Історія, індикатори, конфігурація | Сигнал/намір | Без доступу до брокера |
| AI Engine | Обмежений структурований snapshot | Пропозиція і пояснення | Валідація схеми, бюджет, журнал |
| Risk Engine | Намір, портфель, ринок, ліміти | ALLOW/ADJUST/REJECT та причини | Останній gate перед execution |
| Execution | Дозволений намір | Ордер, fills, reconciliation | Idempotency і state machine |
| Paper Broker | Дані ринку, ордери | Віртуальні fills | Симуляція виконання, не змішує live |
| Backtest | Версіонований dataset | Події та статистика | Той самий контракт стратегій/ризику, контроль часу |
| API | Команди UI і проєкції БД | HTTP/SSE або WS | Auth для локального доступу, валідація, аудит |

## Потік рішення

1. Адаптер приймає подію MEXC, нормалізує її, додає `source_time`, `received_at`, sequence та статус якості.
2. Market Data публікує immutable event; кожен бот отримує той самий snapshot для одного market/timeframe.
3. Стратегія та, за потреби, AI формують кандидата. Правило арбітражу між ними є версіонованою конфігурацією: AI може підтверджувати, відхиляти або генерувати окремий сигнал; конфлікт дає WAIT за замовчуванням.
4. Risk Engine перевіряє дані, портфель, позиції, ліміти та біржові фільтри. Результат записується навіть при REJECT.
5. Execution створює ідемпотентний ордер. Paper Broker формує віртуальні fills; ledger атомарно відображає зміну балансу, комісії, маржу та realized PnL.
6. API віддає проєкції, журнал і health/status у UI.

## Надійність

- Команди мають `command_id` та `idempotency_key`; повтор не створює нового ордера. Стан ордера: `NEW -> ACCEPTED -> PARTIALLY_FILLED -> FILLED` або `CANCELED/REJECTED/UNKNOWN`. Перехід із `UNKNOWN` потребує reconciliation.
- Транзакція БД пов'язує зміну стану ордера, fills і ledger. Outbox-події відправляються після commit; повторна доставка має бути безпечною.
- WS gap, несвіжі дані, неправильний clock drift або невідома ціна переводять інструмент у `DEGRADED`; нові входи блокуються, UI показує причину. Закриття позицій обробляється окремою консервативною політикою.
- При падінні AI алгоритмічні стратегії працюють за налаштуванням; AI-бот переходить у WAIT. При падінні БД execution зупиняється. Redis можна відновити з БД і повторно підписати потоки.

## Межі безпеки

UI не надсилає прямі ордери на MEXC. Backend не експонує торгові ключі в браузер. Live adapter не реєструється без серверного прапорця, валідованого профілю та окремої команди розблокування; деталі — [Risk Engine](RISK_ENGINE.md). Локальний доступ не означає відсутність автентифікації після відкриття мережевого порту.

## Альтернативи

Один контейнер спрощує список сервісів, але ускладнює перезапуск і контроль довготривалих задач. Повний набір мікросервісів додає мережеві й транзакційні ризики на ранньому етапі. Модульний моноліт з окремими процесами дає локальну простоту та чіткі межі модулів. Остаточне розділення процесів можна змінювати після вимірювань.
